## 1. 检索策略

### 1.1 检索范围

| 项 | 内容 |
| --- | --- |
| 时间范围 | 2023 – 2026（LLM Agent 安全方向文献几乎全部集中在此区间） |
| 检索语言 | 中文、英文 |
| 目标数据库 | Web of Science / IEEE Xplore / ACM DL / Scopus / arXiv / 中国知网（CNKI）/ 万方 / 维普 |
| 本次实际覆盖 | 公开网络检索（arXiv、出版社官网、期刊官网、Google Scholar 快照）。**知网/万方需校内 IP 登录，本次未直接检索**，故中文文献条目需按 §7 清单补充核实 |

### 1.2 检索式

按四个概念组做交叉组合（`AND`）：

| 概念组 | 中文关键词 | 英文关键词 |
| --- | --- | --- |
| 主体 | 大语言模型、大模型、智能体、LLM Agent、自主智能体 | large language model, LLM, agent, autonomous agent, tool-using agent |
| 安全 | 提示注入、越权、权限控制、访问控制、最小权限、零信任 | prompt injection, privilege escalation, privilege control, access control, least privilege, zero trust |
| 机制 | 工具调用、能力约束、策略执行、沙箱、隔离 | tool calling, capability restriction, policy enforcement, sandboxing, isolation |
| 场景 | 工业、预测性维护、故障诊断、工业物联网、工控系统 | industrial, predictive maintenance, fault diagnosis, IIoT, ICS, SCADA |

**代表性检索式**：

```
("LLM agent" OR "large language model agent" OR 智能体)
AND ("prompt injection" OR "privilege control" OR "access control" OR 越权)
AND ("tool calling" OR "policy enforcement" OR "capability")

("predictive maintenance" OR 预测性维护 OR 故障诊断)
AND ("large language model" OR "LLM" OR 大模型)
AND ("retrieval-augmented generation" OR "RAG" OR 知识库)
```

### 1.3 筛选标准

- **纳入**：提出安全机制/架构的原始研究；系统综述；工业场景的大模型应用研究；工控安全与访问控制研究。
- **排除**：纯科普/产品介绍、无方法论的行业报告、专利、预印本之外的博客文章。
- **例外**：**安全类的工业界标准文档**（如 OWASP LLM Top 10）虽非期刊论文，但作为**威胁模型来源**予以引用，需注明其性质。

## 4. 研究空白与本课题定位

### 4.1 现有工作的三条主线与各自缺口

| 主线 | 代表工作 | 已解决 | **缺口** |
| --- | --- | --- | --- |
| **策略层权限控制** | P1 Progent | 用策略语言表达工具级权限，可动态调整 | ① 未区分"进程内策略层"与"进程外凭证边界"，把权限控制全部放在**应用进程内**，无法回答"策略层被绕过怎么办"；② 未涉及**字段级**最小权限；③ 无工业场景与数据模型 |
| **设计级抗注入** | P2 CaMeL、P3 Design Patterns | 通过控制流/数据流分离实现可证明的抗注入；归纳出六种模式 | ① 要求**控制流由可信代码驱动**（plan-then-execute 类），与 ReAct 的自由循环存在张力，落地时需改造 Agent 内核；② 停留在**模式与证明**层面，缺少在真实工业系统上的完整落地与度量；③ 未讨论审计完整性与可用性的取舍 |
| **执行隔离** | P4 IsolateGPT | 为每个工具服务提供独立执行环境与权限，切断跨服务流 | ① 面向通用 Agent 应用生态，**不含工业数据模型**；② 隔离粒度是"服务级"，未涉及"同一服务内按调用方裁剪字段"；③ 未讨论 Agent 循环的行为约束（配额、收敛） |

### 4.2 本课题的六个差异点

1. **双层纵深结构的显式提出与论证。**
   把 **L1 进程内策略层**（有完整会话上下文 ⇒ 能做语义级判定、参数改写、配额）与 **L2 进程外凭证边界**（独立进程、独立凭证 ⇒ 不可绕过、能做字段裁剪与权威审计）拆成两层，并明确论证二者**互补且不可互替**，以及各自"拦不住什么"。现有工作（P1–P4）基本只做其中一层，或未做这个区分。

2. **最小权限落实到字段级，且裁剪行为可观测。**
   网关返回载荷中带 `meta.redactedFields`，使"裁剪确实发生"成为**可截图、可对照的验证事实**，而非设计声明。P1–P4 均未把裁剪的**可观测性**作为设计目标。

3. **审计 fail-closed 语义。**
   审计落库失败 ⇒ 调用失败、不返回数据。多数工作把审计当**旁路日志**（异步、失败不影响主流程）。本课题把审计完整性置于可用性之上，并明确记录其代价（业务库故障会导致网关整体拒绝服务）。

4. **用会话级工具配额约束 ReAct 循环收敛。**
   配额不只是防滥用，更是**行为约束**：配额耗尽后返回结构化拒绝原因，迫使 Agent 基于已有信息给出结论，使循环必然终止。文献中少见把"Agent 行为约束"与"访问控制"并置讨论。

5. **工业场景的双库分离 + 唯一出口，把注入后果压缩到"多调用几次工具"。**
   即使提示注入完全成功、模型完全听话，Agent 能做的也只是多调用几次工具——它没有凭证、网关会裁剪。这是"假设模型会被攻陷"的设计思路，与 P2 的"设计级防御"同源，但**实现手段是凭证隔离而非控制流约束**，因而**不需要改造 Agent 内核**。

6. **对框架信任模型限制的显式声明与适配。**
   识别出所选 Agent 框架（OpenClaw）的信任模型是**单用户个人助理**、插件与宿主**同进程**，因此明确**不宣称**插件层是安全边界，而是把多用户权限模型移到网关承载。多数工作在使用某框架时不会显式声明其信任模型边界。

### 4.3 一句话定位

> 现有工作分别回答了"**怎么表达权限策略**"（P1）、"**怎么在设计中保证抗注入**"（P2、P3）、"**怎么隔离工具服务**"（P4）；本课题回答的是"**在一个真实工业 Agent 系统里，如何把这些思路组织成可落地、可审计、可验证的双层纵深结构，并诚实界定每一层的能力边界**"。
